# AWS Skill Builder — Конспект и перевод (Урок 1)

## Коротко о главном

- AWS вырос из внутренних IT-потребностей Amazon в начале 2000-х и стал глобальным облачным провайдером.
- Облачные вычисления: это предоставление IT-ресурсов по требованию через интернет с оплатой по мере использования.
- 6 ключевых преимуществ AWS: переменные затраты, экономия на масштабе, отсутствие гадания по емкости, скорость/гибкость, отсутствие забот о ЦОД, глобальный запуск за минуты.
- Глобальная инфраструктура AWS (Regions + Availability Zones) помогает строить высокодоступные и отказоустойчивые системы.
- Безопасность в AWS работает по модели Shared Responsibility: AWS защищает облако, клиент защищает свои данные/доступ/конфигурации в облаке.

---

## 1) Как появился AWS: исторический контекст

В начале 2000-х Amazon.com был e-commerce сайтом. С ростом пользователей внутренней IT-команде приходилось постоянно масштабировать инфраструктуру: больше серверов, больше хранения, больше вычислительных мощностей.

Чтобы справляться эффективнее, команда стандартизировала инструменты и процессы. Это сработало настолько хорошо, что в 2003 году внутри компании возникла идея: такие подходы могут быть полезны и другим компаниям. Так родилась модель, где бизнес арендует вычисления и хранение по запросу, вместо крупных первоначальных инвестиций в железо.

Ключевые вехи:

- 2004: запуск первого публичного сервиса AWS — Amazon SQS.
- Затем: запуск Amazon S3 (хранилище) и Amazon EC2 (эластичные вычисления).
- Сначала AWS активно использовали стартапы и разработчики, позже — крупный enterprise, госсектор и другие.

Итог: внутреннее решение Amazon превратилось в мирового лидера облачных вычислений.

---

## 2) Что такое облачные вычисления

**Рабочее определение:**

> Облачные вычисления — это предоставление IT-ресурсов по требованию через интернет с оплатой по факту потребления.

Разберем части определения:

- **По требованию (on-demand):** ресурсы создаются, когда нужны, и удаляются, когда больше не нужны.
- **IT-ресурсы:** вычисления, хранилище, сети, базы данных, аналитика и т.д.
- **Через интернет:** управление удаленно из любой точки (через веб-консоль/API/CLI).
- **Pay-as-you-go:** платите только за используемое; де-провижининг прекращает расходы.

Пример: нужно 2000 TB хранения — можно быстро начать с `Amazon S3`; если данные больше не нужны, удаляете их и перестаете платить.

---

## 3) Шесть основных преимуществ AWS Cloud

### 1. Обмен фиксированных затрат на переменные

В классическом on-prem требуются большие капитальные вложения: помещение, оборудование, команда, эксплуатация. В AWS счет меняется от месяца к месяцу в зависимости от реального потребления.

**Плюс:** можно стартовать с малого без огромного upfront-бюджета.

### 2. Экономия за счет масштаба

AWS закупает оборудование в больших объемах для дата-центров по всему миру и передает часть этой экономии клиентам.

### 3. Не нужно гадать с емкостью

On-prem часто требует закупать мощности "впрок" по прогнозу, который легко ошибочен:

- Переоценили рост — переплатили за простаивающее железо.
- Недооценили рост — получите дефицит мощностей и риски для клиентского опыта.

В AWS масштабирование обычно занимает минуты, а не недели/месяцы.

### 4. Рост скорости и гибкости

Быстро поднимаете тестовые среды, проводите эксперименты, неудачные варианты удаляете без долгих последствий.

**Результат:** меньше времени на рутину, больше — на инновации.

### 5. Меньше расходов на эксплуатацию дата-центров

Не нужно заниматься физическим слоем: размещением, подключением, питанием, охлаждением серверов.

### 6. Выход на глобальный рынок за минуты

Вместо строительства своих площадок в другой стране можно развернуться в нужном AWS Region.

---

## 4) AWS Global Infrastructure и зачем она нужна

AWS строит инфраструктуру по миру не только ради географии, но и ради **доступности**.

### Базовые понятия

- **Region** — географический регион AWS (например, Ирландия, Сингапур, Токио и т.д.).
- **Availability Zone (AZ)** — изолированная зона доступности внутри региона.
- В каждом регионе обычно 3+ AZ для резервирования.
- В каждой AZ — один или несколько отдельных дата-центров с резервированием питания, сети и каналов связи.

### High Availability и Fault Tolerance

- **High Availability (высокая доступность):** сервис остается доступным при сбоях отдельных компонентов с минимальным downtime.
- **Fault Tolerance (отказоустойчивость):** система продолжает работу даже при множественных отказах за счет заранее заложенной устойчивости.

### Практический вывод

- Минимум: использовать несколько AZ в одном регионе.
- Для disaster-сценариев: часто нужно проектировать и работу между несколькими регионами (multi-region + failover).

---

## 5) Модель общей ответственности AWS (Shared Responsibility Model)

Кто отвечает за безопасность? **И AWS, и клиент**, но в разных слоях.

### AWS отвечает за безопасность **of the cloud**

- Физическая безопасность ЦОД.
- Безопасность инфраструктурной сети.
- Слой виртуализации/гипервизор.

### Клиент отвечает за безопасность **in the cloud**

- ОС (обновления/патчи, hardening).
- Конфигурации приложений.
- Управление доступом (IAM, роли, ключи, политики).
- Защита и шифрование данных.

Критично: AWS не "заходит" в вашу ОС и не ставит патчи за вас (в типичных IaaS-сценариях).

---

## 6) Cloud in Real Life: пример e-commerce компании

Сценарий: компания хочет глобально масштабировать онлайн-магазин.

Что дает AWS на практике:

- Размещение ближе к пользователям (меньше задержка).
- Развертывание в нескольких регионах для глобального охвата.
- Минимум две AZ для высокой доступности и failover.
- Фокус команды на бизнес-рисках и комплаенсе (например, карточные данные), а не на замках в дата-центре.

---

## Термины (быстрый словарь)

- **On-demand** — по требованию, в момент необходимости.
- **Pay-as-you-go** — оплата только за использованное.
- **Region** — географический регион AWS.
- **AZ** — изолированная зона доступности внутри региона.
- **High Availability** — минимальный простой при отказах.
- **Fault Tolerance** — работа даже при нескольких отказах.
- **Shared Responsibility Model** — разделение зон ответственности по безопасности.

---

## Что важно запомнить для практики и собеседований

1. Облако = скорость запуска + гибкость + переменные затраты.
2. HA достигается минимум через multi-AZ архитектуру.
3. DR-уровень обычно требует multi-region подхода.
4. Безопасность всегда совместная: AWS + клиент.
5. Большая часть инцидентов у клиентов связана не с "взломом AWS", а с ошибками конфигурации доступа.

====================== МОДУЛЬ 2: AMAZON EC2 ========================
====================================================================

## Коротко о главном (модуль 2)

- `Amazon EC2` — это виртуальные серверы (VM) в AWS с быстрым запуском и оплатой за фактическую работу инстансов.
- EC2 дает контроль над ОС, софтом, размером инстанса, сетью и масштабированием.
- Типы инстансов подбираются под задачу: general purpose, compute, memory, accelerated, storage optimized.
- В AWS все сводится к API-вызовам: через Console, CLI или SDK.
- Для надежности и эффективности используют Auto Scaling, Load Balancing и слабосвязанную архитектуру через SQS/SNS.

---

## 1) Amazon EC2 на высоком уровне

`EC2` предоставляет "сырую" вычислительную мощность для приложений: веб-серверов, API, аналитики, batch-задач и т.д.

Почему это удобно:

- запуск за минуты, а не недели/месяцы как при on-prem закупке;
- можно остановить/удалить инстанс, когда он не нужен;
- платите только за использование (для базового сценария On-Demand).

EC2-инстанс = виртуальная машина. На одном физическом хосте могут жить инстансы разных клиентов (**multi-tenancy**), а изоляцию и распределение ресурсов обеспечивает **hypervisor**. Это зона ответственности AWS.

Что контролирует клиент:

- выбор ОС (Linux/Windows),
- установка приложений,
- конфигурация сети и доступа,
- размер и тип инстанса.

---

## 2) Семейства инстансов EC2

Выбор инстанса = выбор баланса `CPU / RAM / storage / network` под конкретную нагрузку.

- **General Purpose** — универсальный баланс; хороший старт по умолчанию.
- **Compute Optimized** — вычислительно тяжелые задачи (HPC, game servers, ML-инференс/часть тренировок).
- **Memory Optimized** — большие объемы данных в памяти (in-memory DB, кэши, real-time обработка).
- **Accelerated Computing** — GPU/FPGA/другие ускорители для графики, ML, pattern matching.
- **Storage Optimized** — высокопроизводительная локальная дисковая нагрузка.

Практика: сначала берите консервативный размер, затем измеряйте метрики и делайте rightsizing. "Больше" не всегда "лучше" — почти всегда "дороже".

---

## 3) Как взаимодействовать с AWS: Console, CLI, SDK

В AWS практически любое действие — это API-вызов.

### AWS Management Console

- удобна для обучения, первых запусков и визуального контроля;
- но в production ручной "point-and-click" повышает риск ошибок.

### AWS CLI

- управление через команды в терминале;
- удобна для скриптов и автоматизации повторяемых операций.

Примеры команд:

```bash
aws ec2 run-instances ...
aws ec2 describe-availability-zones
```

### AWS SDK

- вызовы AWS API из кода (Python, Java, JavaScript и др.);
- база для инфраструктурной автоматизации и интеграций.

---

## 4) Базовый запуск EC2 под веб-сервер (через Console)

Ключевые шаги из демо:

1. Выбрать имя инстанса.
2. Выбрать `AMI` (образ ОС), например `Amazon Linux`.
3. Выбрать тип инстанса (пример в уроке: `t2.micro`).
4. Назначить `key pair` для доступа (public key в инстанс, private key хранится у вас).
5. Настроить сеть/доступ (например, разрешить HTTP для веб-сервера).
6. Указать storage (например, `EBS gp3`, 8 GiB).
7. В `User Data` добавить bootstrap-скрипт (установка и запуск Nginx).
8. Запустить инстанс и проверить по public IP.

Практический акцент: `User Data` — хороший базовый шаг к immutable/автоматизированным окружениям без ручной пост-настройки.

---

## 5) Модели оплаты EC2

- **On-Demand**: плата за фактическое время работы, без долгого коммита.
- **Savings Plans**: скидки за обязательство по уровню потребления (1 или 3 года), до ~72%.
- **Reserved Instances (RI)**: для предсказуемых steady-state нагрузок, до ~75%; варианты оплаты: all/partial/no upfront.
- **Spot Instances**: использование свободной емкости с большими скидками (до ~90%), но возможен отзыв инстанса (обычно с 2-минутным предупреждением).
- **Dedicated Hosts**: выделенный физический сервер под одного клиента (комплаенс, лицензирование, изоляция).

Базовая стратегия: начать с On-Demand, собрать профиль потребления, затем оптимизировать через Savings Plans/RI/Spot, где это безопасно для SLA.

---

## 6) Масштабирование: vertical vs horizontal

- **Scale Up (vertical)**: увеличить мощность одного инстанса (больше vCPU/RAM).
- **Scale Out (horizontal)**: добавить больше инстансов и обрабатывать запросы параллельно.

В большинстве веб-нагрузок горизонтальное масштабирование предпочтительнее: выше отказоустойчивость и гибче управление пиками.

---

## 7) EC2 Auto Scaling

`EC2 Auto Scaling` автоматически:

- добавляет инстансы при росте нагрузки,
- удаляет/останавливает лишние при падении,
- поддерживает нужную (desired) емкость.

Для принятия решений используются метрики, обычно через `Amazon CloudWatch` (CPU, latency, custom metrics).

Практика:

- держать минимально 2+ инстанса в разных AZ;
- задать health checks;
- масштабировать tiers независимо (frontend и backend отдельно).

---

## 8) Балансировка трафика: ELB

`Elastic Load Balancing (ELB)` распределяет входящий трафик по инстансам и снимает часть операционной нагрузки (патчи, отказоустойчивость балансировщика и т.п.) с команды.

Плюсы:

- равномерная загрузка инстансов,
- меньше перегрузок и простоев,
- упрощение архитектуры (frontend знает endpoint балансировщика, а не каждый backend).

Итог: ELB + Auto Scaling = базовый шаблон для эластичной и устойчивой веб-архитектуры.

---

## 9) Messaging & Queuing: SQS и SNS

### Зачем

Прямые интеграции "сервис A -> сервис B" создают **tight coupling**: сбой B часто бьет по A.

### Amazon SQS

- очередь сообщений (буфер),
- сервисы не обязаны быть онлайн одновременно,
- сообщения сохраняются до обработки,
- снижает риск каскадных отказов.

### Amazon SNS

- pub/sub уведомления "сейчас" (push),
- fan-out в разные подписчики,
- каналы: email, SMS, mobile push и др.

Коротко: SQS — про буферизацию и надежную асинхронность, SNS — про оперативную рассылку событий/уведомлений.

---

## Что важно запомнить для практики и собеседований (модуль 2)

1. EC2 = управляемые виртуальные серверы с быстрым provisioning и гибкой оплатой.
2. Подбор instance family всегда от профиля нагрузки, не "на глаз".
3. Production = автоматизация через CLI/SDK/IaC, а не ручной клик в консоли.
4. Базовая отказоустойчивость: multi-AZ + Auto Scaling + Load Balancer.
5. Слабая связность через очереди повышает устойчивость системы.

========= МОДУЛЬ 3: MANAGED COMPUTE, LAMBDA И CONTAINERS ==========
====================================================================

## Коротко о главном (модуль 3)

- `EC2` дает максимальный контроль, но требует операционного управления инстансами.
- Managed-сервисы переносят значительную часть рутины на AWS.
- `AWS Lambda` — serverless/FaaS: запускает код по событию, автоматически масштабируется, максимум 15 минут на один запуск.
- Контейнеры решают проблему переносимости; в AWS ключевые сервисы: `ECR`, `ECS`, `EKS`, `Fargate`.
- Есть purpose-built сервисы под частные задачи: `Elastic Beanstalk`, `AWS Batch`, `Lightsail`, `Outposts`.

---

## 1) Unmanaged vs Managed vs Serverless

### Unmanaged (пример: EC2)

Вы управляете:

- ОС и патчами,
- масштабированием,
- конфигурациями серверов и окружения.

AWS при этом управляет базовой инфраструктурой (физика, сеть, гипервизор).

### Managed

AWS берет на себя больше эксплуатационных задач. Вы задаете конфигурацию и требования, а сервис поддерживается AWS.

Примеры из прошлых модулей: `ELB`, `SQS`, `SNS`.

### Serverless

Вы не управляете серверами вообще: AWS берет provisioning, scaling, HA, maintenance. Вы фокусируетесь на коде и логике приложения.

Практический критерий выбора: чем выше требования к низкоуровневому контролю, тем ближе к unmanaged; чем важнее скорость и простота, тем ближе к managed/serverless.

---

## 2) AWS Lambda (FaaS)

`AWS Lambda` запускает функцию в ответ на триггер (событие).

Примеры триггеров:

- загрузка файла,
- событие из очереди/стрима,
- HTTP-запрос,
- расписание.

Что важно:

- автоматическое масштабирование от единичных до массовых вызовов;
- высокая доступность "из коробки";
- нет управления серверами и патчами;
- ограничение одного запуска функции: до `15 минут`.

Когда подходит:

- event-driven сценарии,
- обработка файлов/изображений,
- интеграционная логика,
- легкие API/automation-задачи.

Когда стоит подумать дважды:

- долгие непрерывные вычисления,
- тяжелые stateful-процессы, которые сложно дробить на короткие шаги.

Lambda поддерживает популярные runtime (например, Python, Java, Node.js), а также кастомные runtime.

---

## 3) Контейнеры: зачем и как в AWS

Контейнер упаковывает код + runtime + зависимости + конфиг в переносимую единицу. Это снижает классическую проблему "works on my machine".

Плюсы контейнеров:

- одинаковое поведение в разных средах,
- быстрый старт,
- лучшая плотность утилизации ресурсов.

Но в реальности нужен оркестратор, который управляет жизненным циклом контейнеров.

---

## 4) Оркестрация контейнеров: ECS и EKS

### Amazon ECS

- нативный AWS-оркестратор,
- проще старт и эксплуатация,
- хорош для сценариев, где важна глубокая интеграция с AWS.

### Amazon EKS

- управляемый Kubernetes в AWS,
- больше гибкости и переносимости Kubernetes-подходов,
- подходит для крупных/гибридных и стандартизированных K8s-сред.

Оба сервиса решают задачи:

- запуск/остановка контейнеров,
- авто-масштабирование,
- self-healing,
- rolling updates и операционное управление кластерной нагрузкой.

---

## 5) Где хранятся образы и где крутятся контейнеры

### Amazon ECR

`ECR` — managed registry для контейнерных образов.

Пайплайн в упрощенном виде:

1. Собрали образ приложения.
2. Запушили образ в `ECR`.
3. Оркестратор (`ECS`/`EKS`) подтянул образ и развернул сервис.

### Compute для контейнеров: EC2 или Fargate

- **EC2 launch type**: больше контроля, но вы управляете парком виртуальных машин.
- **AWS Fargate**: serverless-подход для контейнеров; серверы скрыты, вы управляете только контейнерной задачей.

Кратко: EC2 — контроль, Fargate — простота и скорость операций.

---

## 6) Другие compute-сервисы под конкретные задачи

### AWS Elastic Beanstalk

Платформа для упрощенного деплоя приложений на базе EC2. Вы отдаете код и настройки, сервис поднимает окружение (инстансы, scaling, балансировку и т.п.).

### AWS Batch

Для batch/HPC-нагрузок: массовая обработка данных, сложные вычисления, симуляции. AWS управляет инфраструктурой выполнения и масштабированием.

### Amazon Lightsail

Упрощенный и часто более предсказуемый по стоимости вариант для типовых веб-приложений и сайтов.

### AWS Outposts

Гибридный сценарий: AWS-сервисы в on-prem окружении с консистентным опытом управления. Нужен для low latency, data residency и других hybrid-требований.

---

## Что важно запомнить для практики и собеседований (модуль 3)

1. Выбор compute-модели — это компромисс "контроль vs операционная простота".
2. Lambda сильна в event-driven и коротких задачах, но имеет лимит по времени выполнения.
3. Контейнеры решают переносимость, оркестраторы — эксплуатацию в масштабе.
4. `ECS/EKS + ECR + (EC2|Fargate)` — базовый конструктор контейнерной платформы в AWS.
5. Purpose-built сервисы сокращают time-to-market, если кейс совпадает с их сильными сторонами.

---

## Мини-чеклист после этого модуля

- Определи для своего сервиса: `EC2`, `Lambda`, контейнеры или смешанная модель.
- Если контейнеры: выбери `ECS` или `EKS` и объясни почему.
- Реши, где запускать контейнеры: `EC2` или `Fargate`.
- Проверь, есть ли у твоей задачи готовый purpose-built сервис вместо "собирать все вручную".
- Зафиксируй границы ответственности команды в выбранной модели (patching, scaling, security).

======= МОДУЛЬ 4: REGIONS, EDGE, REDUNDANCY И CLOUD FORMATION ======
====================================================================

## Коротко о главном (модуль 4)

- Выбор AWS Region зависит от `compliance`, `proximity`, `feature availability` и `pricing`.
- Для надежности используют `multi-AZ`, а для более серьезных сценариев — `multi-Region`.
- `CloudFront` ускоряет доставку контента через edge locations и снижает задержку для пользователей.
- `Route 53` помогает маршрутизировать пользователей к приложениям, а `Outposts` выносит AWS-сервисы ближе к on-prem.
- `Infrastructure as Code` и `CloudFormation` позволяют одинаково и повторяемо разворачивать инфраструктуру в разных аккаунтах и регионах.

---

## 1) Как выбирать Region

У AWS Region нет "универсально лучшего" варианта. Выбор всегда зависит от бизнес-ограничений.

### 1. Compliance

Сначала проверьте регуляторные требования. Если данные обязаны оставаться в стране или регионе, это главный критерий.

Примеры:

- финансовые данные могут подпадать под локальные законы о хранении;
- GDPR требует особого обращения с персональными данными в ЕС;
- для государственных сценариев могут быть нужны специальные регионы с усиленными требованиями.

Практический вывод: если закон диктует размещение данных, он важнее удобства, цены и даже близости к пользователям.

### 2. Proximity

Чем ближе Region к пользователям, тем ниже latency и выше отзывчивость приложения.

### 3. Feature availability

Не все сервисы и фичи доступны во всех регионах одновременно. Иногда ближайший регион просто не поддерживает нужную возможность.

### 4. Pricing

Даже при одинаковых сервисах стоимость эксплуатации может различаться из-за налогов, энергии и локальных условий.

---

## 2) Redundancy: multi-AZ и multi-Region

### Multi-AZ

Размещение ресурсов в нескольких Availability Zones помогает пережить локальный сбой одного дата-центра или зоны.

Что это дает:

- высокая доступность;
- меньше простоев;
- быстрее восстановление после аварий;
- лучшее соответствие требованиям к устойчивости.

### Multi-Region

Если целый Region недоступен, можно переключиться на другой Region.

Это уже более сложный уровень архитектуры, но он нужен для критичных систем и планов disaster recovery.

Практический совет: начинайте с multi-AZ, а multi-Region добавляйте только там, где это действительно оправдано бизнесом и SLA.

---

## 3) Edge locations и CloudFront

AWS использует глобальную edge-сеть, чтобы доставлять контент ближе к пользователю.

### Edge locations

- расположены отдельно от Regions;
- используются для ускорения доставки;
- помогают снизить задержку при выдаче контента.

### Amazon CloudFront

`CloudFront` — это CDN, который кэширует и раздает контент из ближайших точек присутствия.

Что можно ускорять:

- изображения;
- видео;
- статические сайты;
- приложения;
- API.

Практический эффект: если мемы, картинки или видео грузятся медленно, CloudFront часто помогает сильнее, чем просто перенос приложения в другой Region.

### Route 53

`Route 53` — это DNS-сервис AWS, который переводит доменное имя в IP-адрес и помогает направлять пользователей к нужным приложениям.

---

## 4) Outposts

`AWS Outposts` позволяет запускать сервисы AWS в on-prem среде.

Когда это полезно:

- нужна очень низкая задержка;
- есть требования по data residency;
- нужно сочетать локальную инфраструктуру и облачные сервисы;
- требуется гибридная модель.

Идея Outposts — дать единый опыт управления и в облаке, и в собственном дата-центре.

---

## 5) Agility и Elasticity

### Agility

`Agility` — это способность быстро адаптироваться к изменяющимся требованиям и быстро разворачивать новые сервисы.

### Elasticity

`Elasticity` — это способность автоматически увеличивать или уменьшать ресурсы в ответ на спрос.

Коротко:

- agility = быстро менять направление;
- elasticity = быстро менять объем ресурсов.

---

## 6) Infrastructure as Code и CloudFormation

Когда нужно развернуть одинаковую инфраструктуру в нескольких регионах или аккаунтах, ручной клик в консоли становится проблемой.

### Почему IaC нужен

- меньше человеческих ошибок;
- повторяемость;
- прозрачные изменения через source control;
- быстрее создание одинаковых окружений.

### CloudFormation

`AWS CloudFormation` позволяет описывать инфраструктуру декларативно в шаблонах.

Суть:

- вы описываете, что хотите получить;
- CloudFormation сам вызывает нужные AWS API;
- в результате создаются одинаковые окружения там, где это нужно.

Это особенно полезно для:

- multi-account deployments;
- multi-region deployments;
- стандартных шаблонов окружений dev/test/prod.

Практический вывод: если у вас есть повторяемая инфраструктура, IaC почти всегда лучше ручной настройки.

---

## 7) Interacting with AWS resources

Для работы с AWS ресурсами используются API, а доступ к ним обычно идет через:

- AWS Management Console;
- AWS CLI;
- AWS SDKs;
- IaC-инструменты вроде CloudFormation.

Важно помнить: разные способы взаимодействия меняют лишь интерфейс работы, но не сам принцип — в основе все равно лежат API-вызовы.

---

## Что важно запомнить для практики и собеседований (модуль 4)

1. Region выбирают не только по географии, но и по compliance и доступности сервисов.
2. Multi-AZ — базовый уровень устойчивости, multi-Region — более продвинутый.
3. CloudFront снижает latency и помогает разгрузить исходный регион.
4. Outposts нужен для гибридных и low-latency сценариев.
5. CloudFormation делает инфраструктуру повторяемой и управляемой как код.

---

## Мини-чеклист после этого модуля

- Определи, какой Region подходит твоему проекту и почему.
- Проверь, нужен ли тебе multi-AZ или multi-Region.
- Реши, нужен ли CloudFront для твоего контента.
- Подумай, можно ли часть инфраструктуры описать через CloudFormation.
- Сравни ручной деплой и IaC для своего сценария.

======= МОДУЛЬ 5: REVIEW, SYNTHESIS И ПРАКТИЧЕСКАЯ СВЯЗКА ==========
====================================================================

## Коротко о главном (модуль 5)

- EC2, Lambda, контейнеры, Regions, Load Balancing и IaC — это не отдельные темы, а строительные блоки одной архитектуры.
- Выбор сервиса почти всегда сводится к балансу между контролем, скоростью разработки, стоимостью и операционной сложностью.
- Устойчивые системы строятся через автоматизацию, разделение ответственности и redundancy на разных уровнях.
- В реальных проектах AWS-сервисы часто комбинируются: compute + networking + storage + delivery + automation.

---

## 1) Как собирать AWS-архитектуру в голове

Удобно думать об AWS так:

- `compute` — где выполняется код;
- `storage` — где лежат данные;
- `networking` — как трафик попадает в систему;
- `delivery` — как быстро контент доходит до пользователя;
- `security` — кто и за что отвечает;
- `automation` — как все это разворачивается повторяемо.

Если смотреть на сервисы через такую схему, становится проще выбирать нужные компоненты.

---

## 2) Типовой путь от простого к зрелому решению

Часто эволюция выглядит примерно так:

1. Запустили приложение на `EC2`.
2. Добавили `ELB` для распределения трафика.
3. Подключили `Auto Scaling` для эластичности.
4. Вынесли асинхронные части в `SQS` или `SNS`.
5. Для отдельных задач добавили `Lambda`.
6. Для контейнеров подключили `ECR` + `ECS/EKS` + `Fargate` или `EC2`.
7. Для повторяемости перевели инфраструктуру на `IaC`.

Это не единственный путь, но он хорошо показывает, как AWS-сервисы складываются в систему.

---

## 3) Когда какой compute использовать

### EC2

Подходит, когда нужен максимальный контроль, доступ к ОС и гибкая настройка окружения.

### Lambda

Подходит для коротких событийных задач и автоматизации без серверного администрирования.

### Containers

Подходят, когда важно переносить приложение между средами и удобно упаковать все зависимости в образ.

### Purpose-built services

Подходят, когда задача уже хорошо совпадает с готовым сервисом, и не хочется собирать все с нуля.

Практический принцип: не выбирайте сервис по моде — выбирайте по рабочей нагрузке.

---

## 4) Как не запутаться в shared responsibility

Хорошее правило:

- AWS отвечает за инфраструктуру и управляемые слои сервиса;
- клиент отвечает за конфигурацию, данные, доступ и бизнес-логику.

Чем выше уровень abstraction сервиса, тем больше задач уходит в сторону AWS. Но полностью "ничего не делать" не получится — безопасность и конфигурация почти всегда остаются на клиенте.

---

## 5) Главные архитектурные паттерны, которые повторяются

### Redundancy

Дублирование критичных компонентов, чтобы один сбой не остановил систему.

### Decoupling

Слабая связность между сервисами, чтобы сбой одного не ломал остальные.

### Automation

Повторяемое создание инфраструктуры и сокращение ручных операций.

### Scalability

Рост системы без полной перестройки архитектуры.

Если запомнить эти четыре идеи, многие сервисы AWS становятся логичными и предсказуемыми.

---

## 6) Практический вывод по всему блоку

AWS дает не просто список сервисов, а набор решений под разные уровни ответственности:

- больше контроля — ближе к `EC2`;
- меньше операционной рутины — ближе к managed и serverless;
- больше повторяемости — через `IaC`;
- больше устойчивости — через `multi-AZ`, `multi-Region`, `Auto Scaling`, `ELB`, `CloudFront`;
- больше гибкости — через комбинацию сервисов.

- Могу ли я описать свой проект через compute, storage, networking, delivery, security и automation?
- Понимаю ли я, где нужен контроль, а где лучше отдать управление AWS?
- Есть ли у меня план на отказ одного инстанса, одной AZ и целого Region?
- Описана ли инфраструктура кодом, а не только в голове?
- Использую ли я правильный сервис под задачу, а не “самый знакомый”?

========= МОДУЛЬ 6: VPC, CONNECTIVITY, TRAFFIC SECURITY ==========
====================================================================

## Коротко о главном (модуль 6)

- `Amazon VPC` — изолированная частная сеть в AWS, где вы сами задаете IP-диапазон и сетевые границы.
- Ресурсы размещаются в `subnets` (public/private), а доступ наружу/внутрь управляется через gateway и маршрутизацию.
- Для подключения к AWS есть несколько подходов: `Client VPN`, `Site-to-Site VPN`, `PrivateLink`, `Direct Connect`.
- Трафик внутри VPC контролируется на двух уровнях: `network ACL` (subnet, stateless) и `security group` (instance, stateful).
- Безопасная сеть в AWS строится как комбинация сегментации, явных правил, шифрованных подключений и отказоустойчивости.

---

## 1) Что такое VPC и зачем он нужен

`VPC` — это ваш приватный сетевой контур в AWS.

Внутри него вы:

- задаете private CIDR (диапазон IP-адресов);
- запускаете ресурсы (`EC2`, `ELB`, базы и др.);
- определяете, что будет публичным, а что останется внутренним.

Три практические выгоды VPC:

- **Безопасность:** изоляция, контроль и мониторинг трафика.
- **Контроль:** полное управление размещением ресурсов и связностью.
- **Скорость операций:** быстрее и проще, чем ручное on-prem сетевое администрирование.

---

## 2) Subnets: как делить сеть

`Subnet` — это часть диапазона VPC.

- **Public subnet**: ресурсы, к которым должен быть доступ из интернета (например, web-tier/ALB).
- **Private subnet**: внутренние компоненты (например, БД, внутренние сервисы, backend).

Базовый шаблон:

- frontend в public subnet;
- data-tier в private subnet;
- связь между ними по нужным портам и явным правилам.

Практика: распределять public/private подсети минимум по 2 AZ для высокой доступности.

---

## 3) Internet Gateway и Virtual Private Gateway

### Internet Gateway (IGW)

Нужен, чтобы разрешить трафику из интернета входить в VPC и выходить из VPC.

Важно: сам факт создания public subnet недостаточен. Нужны еще:

- attached IGW;
- route `0.0.0.0/0` в route table к этому IGW;
- association этой route table с public subnets.

### Virtual Private Gateway (VGW)

Нужен для защищенного VPN-канала между VPC и внешней приватной сетью (on-prem/DC/corp network).

Идея: трафик идет по зашифрованному туннелю, а не как публичный доступ в интернет.

---

## 4) Подключение к AWS: что и когда выбирать

### AWS Client VPN

Managed VPN для удаленных сотрудников и клиентских устройств.

Когда подходит: быстрый масштабируемый remote access без обслуживания VPN-железа.

### AWS Site-to-Site VPN

VPN между площадками (например, branch office/DC <-> VPC).

Когда подходит: шифрованная межсетевая связность и миграционные сценарии.

### AWS PrivateLink

Приватный доступ к сервисам/endpoint без IGW, публичных IP, NAT и без обязательного Site-to-Site VPN.

Когда подходит: безопасный приватный доступ к сервисам в других VPC и сервисным endpoint.

### AWS Direct Connect

Выделенный приватный канал (физическое соединение) между вашей сетью и AWS.

Когда подходит:

- большие объемы передачи данных;
- чувствительность к пропускной способности;
- требования к стабильности канала;
- требования комплаенса/регуляторики.

Практика: частый production-паттерн — `Direct Connect + VPN failover`.

---

## 5) Network ACL и Security Group: ключевая разница

### Network ACL (NACL)

- уровень: **subnet**;
- модель: **stateless** (каждый пакет проверяется отдельно в обе стороны);
- правила: `allow` и `deny`;
- для custom NACL по умолчанию обычно все запрещено, пока явно не разрешите.

### Security Group (SG)

- уровень: **resource/instance** (например, EC2);
- модель: **stateful** (ответный трафик пропускается автоматически для разрешенной сессии);
- правила: только `allow`;
- по умолчанию: inbound закрыт, outbound разрешен.

Коротко:

- NACL = грубый фильтр на границе подсети;
- SG = точечный контроль доступа к конкретному ресурсу.

---

## 6) Поток пакета между подсетями (как это мыслить)

Когда пакет идет `Instance A -> Instance B` в другой subnet:

1. Проходит outbound-правила `SG` у A.
2. Проходит outbound-правила `NACL` у subnet A.
3. Проходит inbound-правила `NACL` у subnet B.
4. Проходит inbound-правила `SG` у B.

На обратном пути:

- `SG` учитывает state и обычно пропускает ответ автоматически;
- `NACL` проверяет снова (stateless) и для inbound, и для outbound.

Практический риск: чаще всего ошибки в связности связаны с несовпадением SG/NACL/route table, а не с самим приложением.

---

## 7) Демо-архитектура VPC (из урока)

В демонстрации строилась базовая сеть:

- 1 VPC (пример CIDR `10.0.0.0/16`);
- 2 private subnets (`10.0.1.0/24`, `10.0.2.0/24`) в разных AZ;
- 2 public subnets (`10.0.3.0/24`, `10.0.4.0/24`) в разных AZ;
- IGW, attached к VPC;
- отдельная public route table с `0.0.0.0/0 -> IGW`;
- association route table с public subnets.

Ключевая мысль: subnet становится действительно public только когда есть корректная маршрутизация к IGW.

---

## 8) Route 53, CloudFront и Global Accelerator

### Amazon Route 53

DNS-сервис: переводит домены в IP, умеет маршрутизировать пользователей по политикам (latency, geolocation, weighted и др.).

### Amazon CloudFront

CDN: кэширует и отдает контент с edge-точек рядом с пользователем для ускорения загрузки.

### AWS Global Accelerator

Ускоряет и стабилизирует доступ к приложению через глобальную сеть AWS, добавляет быстрый failover и улучшение доступности.

Простой ориентир:

- Route 53 — DNS и выбор направления;
- CloudFront — ускорение доставки контента;
- Global Accelerator — оптимизация глобального сетевого пути к приложению.

---

## 9) Cloud in Real Life: VPN vs Direct Connect

Из практического сегмента:

- VPN хорош для гибкого и безопасного подключения, особенно при умеренных объемах.
- Direct Connect лучше для высокой и стабильной полосы, крупных трансферов и чувствительных нагрузок.
- Для отказоустойчивости часто делают VPN как резерв к Direct Connect.
- Для глобальной выдачи контента часто комбинируют Route 53 + CloudFront + multi-Region архитектуру.

---

## Что важно запомнить для практики и собеседований (модуль 6)

1. VPC — это фундамент сетевой изоляции и контроля в AWS.
2. Public/private статус подсети определяется не названием, а gateway + route table + правилами доступа.
3. SG и NACL решают разные задачи и должны проектироваться вместе.
4. VPN и Direct Connect не взаимоисключают друг друга: часто работают в паре.
5. Edge-сервисы (Route 53/CloudFront/Global Accelerator) критичны для глобальной производительности.
